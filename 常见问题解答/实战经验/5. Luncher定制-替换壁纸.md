## 定制Launcher（桌面系统）

最核心、最常见的开发任务

### 路线一：修改系统自带的 Launcher3（原生深度定制）
主要定制点包括：

1. 更改默认壁纸：更换成公司品牌的静态/动态默认壁纸。
   
   **【实战操作】推荐使用“资源覆盖（Resource Overlay）”机制进行无损定制：**
   * **原理**：Android 的默认壁纸由系统核心框架（Framework Resources）管理。不推荐直接修改 `/frameworks/base/` 源码，而是利用 Rockchip 的 overlay 机制，让编译器在打包时自动替换默认壁纸。

   * **深入剖析：为什么 Overlay（资源覆盖）机制可以起作用？**
     * **运行机制**：在编译打包阶段，Android 资源打包工具（AAPT/AAPT2）会根据系统 Makefiles 中定义的 `DEVICE_PACKAGE_OVERLAYS` 变量指定的目录进行检索。如果发现 Overlay 目录下有与系统 AOSP 基础包（如 `frameworks/base/core/res/`）**完全一致的相对路径和文件名**的文件，它就会用这个文件**直接替换掉**系统默认资源。
     * **背后的 Makefiles 依据**：
       1. 在 Rockchip 平台中，全局配置文件 `device/rockchip/common/BoardConfig.mk` 默认注册了通用覆盖目录：
          ```make
          ifeq ($(filter atv box, $(strip $(TARGET_BOARD_PLATFORM_PRODUCT))), )
          DEVICE_PACKAGE_OVERLAYS += device/rockchip/common/overlay
          endif
          ```
          由于产品编译入口 `device/rockchip/rk3399/rk3399_roc_pc_plus/rk3399_roc_pc_plus.mk` 包含了 `device/rockchip/common/BoardConfig.mk`，因此放在 `device/rockchip/common/overlay` 下的定制资源是**默认直接生效**的。
       2. 如果您希望将定制资源限制在当前 RK3399 芯片或特定的 ROC-RK3399-PC-Pro 产品目录下（避免影响其他共用 common 的平台），您**必须**在 `rk3399_roc_pc_plus.mk` 中手动追加自定义的 Overlay 路径，例如：
          ```make
          DEVICE_PACKAGE_OVERLAYS += device/rockchip/rk3399/overlay
          ```

    * **关于分辨率适配与屏幕检测：**
      * **第一步：查看当前连接屏幕的物理属性（ADB 指令）**：
        在开发板正常开机并连接屏幕后，可以在电脑终端通过 ADB 指令快速检测屏幕的实际物理属性：
        ```bash
        # 1. 查看屏幕物理分辨率（例如输出：Physical size: 1920x1080）
        adb shell wm size
        
        # 2. 查看屏幕像素密度/DPI（例如输出：Physical density: 240）
        adb shell wm density
        ```
      * **第二步：屏幕分辨率适配与 `nodpi` 壁纸分辨率避坑**：
        * **壁纸分辨率 $\neq$ 物理屏幕分辨率（`wm size`）**：
          在 Android 系统设计中，默认壁纸的宽度通常是物理屏幕宽度的 **2 倍**（例如 `1920x1080` 的屏幕，默认壁纸分辨率通常为 `3840x1080` 或 `2160x1080`）。这是因为 Android 桌面（Launcher3）默认开启了“壁纸随屏幕滑动（Wallpaper Scrolling）”的视差滚动效果。如果直接放一张 1:1 分辨率（如 1920x1080）的图片，在滑动桌面时会被拉伸模糊甚至导致左右留白。
        * **不同设备类型（`sw600dp` 与 `sw720dp`）的分辨率差异**：
          `sw` 代表 Smallest Width（最小宽度）。系统预置这三个文件夹，其分辨率和比例是有意进行了区分的：
          * `drawable-nodpi`：默认的通用设备壁纸，适配标准比例（通常是竖屏手机或基本比例）。
          * `drawable-sw600dp-nodpi`：专为最小宽度 $\ge 600\text{dp}$ 的设备（如 7 寸平板，多为竖屏）准备。
          * `drawable-sw720dp-nodpi`：专为最小宽度 $\ge 720\text{dp}$ 的大屏设备（如 10 寸平板，车载大屏，或横屏 HDMI 显示器）准备。
          **结论**：在制作自定义壁纸时，无需生搬硬套屏幕物理分辨率，建议直接使用 `find frameworks/base/core/res/res/ -name "default_wallpaper*"` 找出原生 SDK 中对应的图片大小，并按照原图的实际比例和分辨率进行等比设计。
        * **为什么一定要把壁纸放在 `nodpi` 目录？**
          `nodpi` 意为 **“无密度缩放（No Density Scaling）”**。如果把壁纸放在 `hdpi`、`xhdpi` 等文件夹下，Android 的资源管理器会根据屏幕的实际 DPI 对壁纸进行强行像素缩放（插值拉伸或压缩），这极易导致**壁纸边缘模糊**，更严重的是会触发 **内存爆涨（Out Of Memory, OOM）** 导致开机卡动画或 Launcher 崩溃。放在 `nodpi` 下，图片会以 1:1 的原始物理像素进行渲染，内存占用最低且最清晰。

     * **操作步骤**：
       > [!IMPORTANT]
       > **关于壁纸图片后缀名（`.png` 与 `.jpg`）的致命冲突机制**：
       > AAPT/AAPT2 编译器的 Overlay（资源覆盖）机制是**基于文件名和文件后缀进行双重绝对精确匹配**的。
       > * AOSP 官方标准系统壁纸默认是 `default_wallpaper.png`。
       > * 部分芯片厂商（如 Rockchip 瑞芯微）或开发板固件为了压缩镜像大小，经常会将原图替换为 `.jpg` 格式。
       > * **致命后果**：如果底层原生文件是 `.jpg` 格式，而您在 Overlay 目录中放入了 `.png` 文件（或反之），编译系统**完全不会执行覆盖替换**，导致静默失效或出现多后缀同名资源冲突。
       > * **第一步必做**：在制作壁纸前，务必先在 SDK 根目录下执行：`find frameworks/base/core/res/res/ -name "default_wallpaper*"`，确认底层文件的真实后缀。

       1. 准备一张壁纸图片，其**分辨率比例与文件名后缀必须与上一步查询出来的底层原生壁纸 100% 完全对应**（如原生为 `default_wallpaper.png` 则准备 PNG 格式；若原生被改为 `default_wallpaper.jpg` 则准备并重命名为 `default_wallpaper.jpg`）。
       2. **根据项目管理需要，选择以下两种 Overlay 路径方案之一：**
          * **方案 A（全局覆盖）**：直接使用 SDK 已注册的全局 `common` 覆盖目录。
          * **方案 B（平台隔离 - 推荐）**：使用 `rk3399` 专有目录。但**必须**先在当前产品的配置 makefile（如 `device/rockchip/rk3399/rk3399_roc_pc_plus/rk3399_roc_pc_plus.mk`）中添加并注册该 Overlay 路径（推荐使用优先级更高的 `PRODUCT_PACKAGE_OVERLAYS`，它会覆盖 `DEVICE_` 变量）：
            ```make
            PRODUCT_PACKAGE_OVERLAYS += device/rockchip/rk3399/overlay
            ```
       3. 在对应的 Overlay 目录下创建与 Framework 核心框架完全一致的子目录结构：
          ```bash
          # 以 方案 A (device/rockchip/common/overlay) 为例：
          mkdir -p device/rockchip/common/overlay/frameworks/base/core/res/res/drawable-nodpi/
          mkdir -p device/rockchip/common/overlay/frameworks/base/core/res/res/drawable-sw600dp-nodpi/
          mkdir -p device/rockchip/common/overlay/frameworks/base/core/res/res/drawable-sw720dp-nodpi/
          
          # 若使用 方案 B (device/rockchip/rk3399/overlay)，则只需将 common 替换为 rk3399 即可
          ```
       4. 将您的壁纸图片文件（请确保文件名加后缀如 `default_wallpaper.png` 或 `default_wallpaper.jpg` 与原生一致）分别拷贝并替换到上述三个创建好的 `drawable-...-nodpi/` 目录中。
        5. **【核心避坑】强制清理编译缓存与极其高效的单模块编译验证**：
           在 Android 10 中，系统资源主要由 **Soong（新版编译系统）** 接管。常规的增量编译或只清理 `out/target/common/obj/APPS/framework-res_intermediates`（旧版 Make 缓存）极易导致编译器直接复用 Soong 的旧缓存而忽视 Overlay 更改。
           
           * **第一步：彻底粉碎 Make 与 Soong 的双重编译缓存**：
             ```bash
             # 1. 彻底删除 Soong 编译系统关于系统资源的全部中间缓存（核心所在！）
             rm -rf out/soong/.intermediates/frameworks/base/core/res/framework-res/
             
             # 2. 彻底删除 Make 编译系统缓存与已打包好的旧系统 APK
             rm -rf out/target/common/obj/APPS/framework-res_intermediates
             rm -rf out/target/product/rk3399_roc_pc_plus/system/framework/framework-res.apk
             ```

           * **第二步：【极速验证妙招】单独编译资源包（无需等整机打包，仅耗时十几秒）**：
             > [!WARNING]
             > **【致命报错避坑：libvpu already defined】**
             > 如果您直接在根目录下运行 `make framework-res`，会触发类似 `hardware/rockchip/librkvpu/common...libvpu already defined by vendor/rockchip/...` 的报错。这是因为“裸编译”时系统未加载环境变量，导致扫描了多余的板级目录产生同名依赖冲突。
             
             **正确的单模块极速编译姿势**：
             ```bash
             # 1. 加载 Android 编译环境变量
             source build/envsetup.sh
             
             # 2. 选定当前 ROC-PC 的产品编译目标（以自动屏蔽其他板子的冲突库）
             lunch rk3399_roc_pc_plus-userdebug
             
             # 3. 单独构建系统核心资源包
             make framework-res
             ```

           * **第三步：一键打包整机镜像**：
             确认单包编译无误后，即可放心执行整机固件的最终打包：
             ```bash
             ./FFTools/make.sh -d rk3399-roc-pc-plus -j8 -l rk3399_roc_pc_plus-userdebug
             ./FFTools/mkupdate/mkupdate.sh -l rk3399_roc_pc_plus-userdebug
             ```

        6. **【运行时避坑】清除系统壁纸运行时缓存**：
           Android 在系统首次开机后，会将默认壁纸拷贝并缓存至用户数据目录（`/data/system/users/0/`）下。直接升级刷机（不擦除 user-data）依然会显示原先开机产生的老壁纸。请在刷机后通过以下命令强制清理缓存并重启以立即生效（必须通过 adb root 提权才能操作该系统保护目录）：
           ```bash
           # 提升 adb 至 root 权限
           adb root
           
           # 清理壁纸缓存并重启开发板
           adb shell rm /data/system/users/0/wallpaper*
           adb shell reboot
           ```

     * **【实战必看】常见排查方法与避坑诊断：**
       * **排查一：检查原图格式与后缀是否 100% 对应**：
         在源码根目录下执行以下命令查询：
         ```bash
         find frameworks/base/core/res/res/ -name "default_wallpaper*"
         ```
         如果发现底层原生的文件名是 `default_wallpaper.jpg`（部分厂商精简了体积），那么您的 Overlay 文件**必须**同样为 `.jpg`，不能为 `.png`，否则 AAPT2 不会进行有效替换。
        * **排查二：【核心大坑】验证 Overlay 资源是否被 Enforce RRO 机制剥离**：
          > [!IMPORTANT]
          > **Android 10+ 强制 RRO（Runtime Resource Overlay）机制**：
          > 在 Android 10+ 中，如果全局配置启用了 `PRODUCT_ENFORCE_RRO_TARGETS := framework-res`，编译系统为了模块化解耦，会**强制拦截所有的 build-time 静态 Overlay 覆盖，绝对不会将其编译进 `framework-res.apk` 本身**！
          > * **表现**：如果您直接用 `unzip -l` 解包 `framework-res.apk`，里面看到的**永远是默认的原生图片**，大小和后缀均没有任何变化。但这并不代表替换失败！
          > * **去向**：系统在打包时，会自动将您的 Overlay 剥离出来，**动态生成一个独立的 RRO 覆盖包**并输出到 `product` 或 `vendor` 分区下。
          
          **正确的验证方法**：
          在源码根目录下执行以下命令，解包**自动生成的 RRO 资源包**进行验证：
          ```bash
          # 1. 查找自动生成的 RRO APK
          find out/target/product/ -name "framework-res__auto_generated*.apk"
          
          # 2. 解包并过滤该 RRO APK 中的壁纸（输出的大小应为您自定义图片压缩后的大小，如 1M 左右）
          unzip -l out/target/product/rk3399_roc_pc_plus/product/overlay/framework-res__auto_generated_rro_product.apk | grep "default_wallpaper"
          ```
        * **排查三：检查 Makefile 中 common 覆盖是否被过滤**：
          在 `device/rockchip/common/BoardConfig.mk` 中，如果产品类型被定义为 `atv` 或 `box`（电视盒子），公共 overlay 目录会被 `ifeq` 条件直接过滤掉：
          `ifeq ($(filter atv box, $(strip $(TARGET_BOARD_PLATFORM_PRODUCT))), )`
          这种情况下，必须采用 **方案 B** 手动在产品 `.mk` 中追加 `PRODUCT_PACKAGE_OVERLAYS += device/rockchip/rk3399/overlay`。

2. 定制默认桌面布局（图标/快捷方式）：

    - 在桌面预置常用 App 的图标位置（例如让 Chrome、Settings 或者您的自定义预装 App 默认出现在桌面上）。
    - 移除或保留底部的快捷栏（Hotseat）图标。
    - 修改对应的配置文件：/packages/apps/Launcher3/res/xml/default_workspace_5x5.xml。

   * **原理**：Launcher3 的默认布局由 XML 配置文件决定。在您的 SDK 中，主要的网格配置文件为 `/packages/apps/Launcher3/res/xml/default_workspace_5x5.xml`。
   * **操作步骤**：
     1. 打开 `default_workspace_5x5.xml` 配置文件。
     2. 若要预置自定义 App 的图标位置，在 xml 中添加 `<favorite>` 标签：
        ```xml
        <favorite
            launcher:screen="0"
            launcher:x="1"
            launcher:y="1"
            launcher:packageName="com.example.fireflydemo"
            launcher:className="com.example.fireflydemo.MainActivity" />
        ```
        *(其中 `screen` 表示第几屏，`x` 和 `y` 表示在 5x5 网格中的坐标，从 0 开始算起。)*
     3. 若要修改底部常驻快捷栏（Hotseat）图标，修改带有 `launcher:container="-101"` 的节点。

3. 隐藏或移除 Google 顶部搜索栏：对于无梯度的国内系统，默认的谷歌搜索栏通常无法使用且占用桌面空间，可以通过修改源码将其彻底隐去。
4. 修改图标网格大小：如把 5x5 网格改为 4x4 或 3x3。

### 路线二：使用第三方 Custom Launcher 替换原生桌面（专有设备定制）
如果您有自己开发好的专用 App（例如数字标牌展示系统、一体机交互界面、智能工控 App），希望设备一开机就直接进入您的 App 且不允许用户退出到普通桌面（即 Kiosk 亭屏模式）：

1. 屏蔽原生 Launcher3：在源码编译配置文件（device.mk）的 PRODUCT_PACKAGES 中，将 Launcher3 或 Launcher3QuickStep 模块剔除。
2. 预置您的主屏 App 为系统级应用：把您的自定义 Launcher 放入 preinstall/ 中，并确保其 AndroidManifest.xml 中配置了主屏过滤项：
```xml
<application
    android:label="@string/app_name"
    android:icon="@mipmap/ic_launcher">
    <activity
        android:name=".MainActivity"
        android:exported="true">
        <intent-filter>
            <!-- 核心！这告诉系统你的 App 是主屏幕/桌面 -->
            <category android:name="android.intent.category.HOME" />
            <!-- 如果要让它取代锁屏（可选） -->
            <category android:name="android.intent.category.DEFAULT" />
            <!-- 如果要支持长按电源键唤醒（可选） -->
            <category android:name="android.intent.category.LAUNCHER_APP" />
            <action android:name="android.intent.action.MAIN" />
        </intent-filter>
    </activity>
</application>
```

### 路线三：基于 RRO（运行时资源覆盖）机制实现 App/Launcher3 极速动态换肤（高级实战）

在开发工业平板、车载中控或智能终端等 RK3399 自研整机产品时，客户经常要求有“深色/浅色主题一键切换”或“多套企业 UI 皮肤动态切换”的功能。利用 Android 原生的 **RRO (Runtime Resource Overlay)** 技术，我们可以做到 **目标 App/Launcher 一行代码都不用改，即可实现极其平滑的动态换肤**。

#### 1. RRO 换肤核心优势：
* **零侵入**：不需要在 Launcher3 或核心 App 中集成任何复杂的换肤 SDK。
* **支持范围广**：不仅支持动态替换图片、图标、文字颜色，甚至连 **布局 Layout XML 文件** 都能直接替换。
* **性能极佳**：由系统底层 AssetManager 重定向实现，开销为零，性能等同于原生资源读取。

---

#### 2. 实战演练：为系统桌面 Launcher3 定制一套“科技深色”皮肤

##### 步骤一：创建皮肤包 Overlay 目录与配置
在您的自定义目录下（例如在 `device/rockchip/rk3399/overlay/` 或 `packages/overlays/Launcher3DarkOverlay/`）创建项目，编写 `AndroidManifest.xml`：

```xml
<manifest xmlns:android="http://schemas.android.com/apk/res/android"
    package="com.android.launcher3.overlay.dark"> <!-- 皮肤包自身的包名 -->
    
    <!-- targetPackage 指向目标桌面的包名，isStatic="false" 代表这是一个可以动态开关的 RRO 插件 -->
    <overlay 
        android:targetPackage="com.android.launcher3" 
        android:isStatic="false" 
        android:priority="1"/>
</manifest>
```

##### 步骤二：放置您需要覆盖替换的换肤资源
在皮肤包项目内建立 `res/` 文件夹。例如我们要修改桌面的壁纸或某些特定文字颜色：
* **替换桌面配色**：在 `res/values/colors.xml` 中写入要覆盖的色值名：
  ```xml
  <resources>
      <!-- 覆盖原生桌面的主背景或文字配色 -->
      <color name="workspace_icon_text_color">#FF00FF</color>
  </resources>
  ```
* **替换图标或壁纸**：在 `res/drawable-nodpi/` 文件夹中放入同名图片。

##### 步骤三：编写皮肤包的 Soong 编译脚本 `Android.bp`
在皮肤包项目根目录下新建 `Android.bp` 文件，声明编译为 product 分区下的资源插件包：
```blueprint
android_app {
    name: "Launcher3DarkOverlay",
    sdk_version: "current",
    product_specific: true, // 编译并打包输出至 product 分区下的 overlay 目录
    certificate: "platform",
    aaptflags: ["--keep-raw-values"],
}
```

##### 步骤四：配置与整机编译
1. 在您的产品 Makefile（如 `rk3399_roc_pc_plus.mk`）中的 `PRODUCT_PACKAGES` 字段追加注册我们的皮肤包：
   ```make
   PRODUCT_PACKAGES += Launcher3DarkOverlay
   ```
2. 运行整机打包编译：
   ```bash
   ./FFTools/make.sh -d rk3399-roc-pc-plus -j8 -l rk3399_roc_pc_plus-userdebug
   ```
   编译成功后，皮肤包 APK 会自动输出至设备的 `/product/overlay/Launcher3DarkOverlay.apk` 中。

#### 3. 运行时如何动态一键切换皮肤？

开发板正常开机后，在自研系统设置 App 中（或直接在 adb 命令行中）调用 OMS (Overlay Manager Service) 提供的服务控制命令即可秒级生效，无需重启桌面：

* **开启“科技深色”皮肤**：
  ```bash
  adb shell cmd overlay enable com.android.launcher3.overlay.dark
  ```
* **关闭并回滚到系统默认皮肤**：
  ```bash
  adb shell cmd overlay disable com.android.launcher3.overlay.dark
  ```
* **查看当前系统所有的皮肤包及其生效状态**：
  ```bash
  adb shell cmd overlay list
  ```

#### 4. 普通商业 App 应用商店分发的局限性与突破
对于从各大应用商店分发的非系统应用：
* **安全限制**：由于 Android 安全机制限制，非特权分区（即非 `/product/overlay` 等特权目录）下的 RRO 皮肤包默认无法加载。
* **突破方法（同签名 RRO）**：在 Android 10+ 中，如果您的皮肤包 APK 与目标 App 采用**完全相同的签名**，则该 RRO 包同样可以被正常安装并动态激活，这极其适合作为“官方皮肤扩展插件”模式分发。
