## 工具（upgrade_tool）的准备
要用到的工具：rk3399_Android10.0/RKTools/linux/Linux_Upgrade_Tool/Linux_Upgrade_Tool_v1.65.zip

每个固件对应的upgrade_tool版本不一样，要使用正确的版本。

1. 从源码的`RKTools/linux/Linux_Upgrade_Tool`中拿到压缩包
2. 解压
3. 把工具upgrade_tool和配置文件config.ini复制到全局目录，然后修改权限

```bash
# 1. 将新版 v1.65 工具和配套的 config.ini 复制到系统全局目录
sudo cp /home/wangwu/firefly/3399-pro/tools/Linux_Upgrade_Tool_1.65/Linux_Upgrade_Tool_v1.65/upgrade_tool /usr/local/bin/upgrade_tool
sudo cp /home/wangwu/firefly/3399-pro/tools/Linux_Upgrade_Tool_1.65/Linux_Upgrade_Tool_v1.65/config.ini /usr/local/bin/config.ini

# 2. 修改权限，确保 root 用户和系统可以正常执行它
sudo chown root:root /usr/local/bin/upgrade_tool
sudo chmod a+x /usr/local/bin/upgrade_tool

# 3. 使用升级后的全局新版工具在 MaskROM 模式下刷写固件
sudo upgrade_tool uf '/home/wangwu/firefly/3399-pro/rk3399_Android10.0/rockdev/Image-rk3399_roc_pc_plus/ROC-RK3399-PC-Pro_Android10_HDMI_260527.img'
```
4. 运行以下命令，确认输出的版本是 Upgrade Tool v1.65： 

```bash
upgrade_tool -v
```

> ef指令，是erase flash，执行后，再次开机，系统进入recovery模式。这个擦除指令，擦除了flash中的bootloader，所以只能进入recovery模式，无法进入loader模式。

recovery 状态下，无法直接使用 upgrade_tool 的 ef 指令。
分析
adb devices 显示 recovery 意味着设备当前处于安卓的恢复模式（Recovery Mode）。在这个状态下，USB 通信使用的是 ADB 协议，而不是 Rockchip 的 Rockusb 烧录协议。 upgrade_tool 工具只能识别并通信处于 Loader 模式 或 MaskROM 模式 的设备。如果在 recovery 状态下直接运行 upgrade_tool，工具会提示找不到设备（No Found Rockusb Device）。

## 刷机的步骤和注意事项
第一步：通过 ADB 命令让设备进入 Loader 模式

 adb shell reboot loader

执行此命令后，设备会重启并自动进入 Loader 模式。此时，Rockchip 的 USB 驱动会被激活，upgrade_tool 就能正确识别设备了。

第二步：确认设备已进入 Loader 模式
您可以通过运行 upgrade_tool（不带参数）来确认设备是否被正确识别：

sudo upgrade_tool

第三步：使用 ef 指令擦除并烧录（非必须）
一旦设备处于 Loader 模式，您可以使用 ef 指令擦除 Flash。

IMPORTANT

在 Linux 的 upgrade_tool 中，使用 ef 擦除指令时，必须指定固件镜像文件（工具需要从镜像中提取 loader 并加载到内存中才能执行擦除）

第四步：使用uf指令烧写固件

瑞芯微（Rockchip）的芯片设计中，MaskROM 模式是硬编码在 CPU 内部只读存储器中的，永远不可能被损坏或刷死。

ef，uf的使用场景：

注意：日常开发中最标准、最常用的刷机方式。
场景 A：日常开发与同系统升级（如：Android 10 升级到另一个 Android 10 编译版本）
操作：直接 uf 烧录，无需 ef。

场景 B：跨系统或大版本升级（如：Android 7.1 升级到 Android 10，或 Android 刷成 Ubuntu）
操作：强烈建议先 ef 擦除，再 uf 烧录。
解析：由于不同大版本系统的分区表（Parameter）布局完全不同，直接 uf 有可能因为旧分区表的数据残留而导致烧录报错或开机卡死。先 ef 可以确保 Flash 被彻底格式化，以最干净的状态迎接新系统。

## 常见问题
为什么会出现“指示灯亮一下就不亮了，无法开机”？
这是因为您之前的操作（或者擦除指令）已经清除了 Flash（eMMC/SPI Flash）中的 Bootloader。当设备通电后，CPU 启动并寻找引导程序，发现 Flash 中没有任何有效代码，于是 CPU 会自动挂起，指示灯熄灭——这正是设备准备进入 MaskROM（最底层恢复）模式的正常表现。

如何重新让电脑识别并进行刷机？
请按照以下步骤，重新将设备与电脑连接，以进入 MaskROM 模式：

拔掉开发板的所有电源（DC 电源线或 Type-C 供电线）。
拔出开发板上的 SD 卡（如果有的话）。
连接 USB 数据线：确保 Type-C 数据线一头连接在电脑上，另一头连接在开发板的 OTG 接口上（请确认是带有 OTG 标识的那个 Type-C 接口，通常靠近 HDMI 接口）。
按住 RECOVERY 键：用手按住开发板上的 RECOVERY（恢复）键不要松开。
插入电源：接通开发板的电源（DC 适配器或供电线）。
松开按键：等待约 2~3 秒后，松开 RECOVERY 键。

验证与刷机
完成上述步骤后，请在您的 Linux 终端中运行以下命令查看设备是否已被电脑识别： lsusb

为了确保系统稳定性，强烈建议先 ef 擦除，再 uf 刷写。
即使您不执行 ef 而直接运行 uf，也无法保留设备中的原有用户数据。

1. 为什么 ef 之后只能进入 MaskROM 模式，而进不去 Loader 模式？
简单来说：因为 ef（擦除）已经把进入 Loader 模式所必须的“启动软件”给抹掉了。

Loader 模式（软件级刷机模式）： 它依赖于 Flash（eMMC）中已经存在且完好的引导程序（Bootloader/Loader）。设备通电时，CPU 先加载运行 Flash 中的 Loader，然后 Loader 检测到 USB 连线或按键，从而进入 Loader 模式等待电脑指令。
MaskROM 模式（硬件级刷机模式）： 它是硬编码在 CPU 内部 ROM 芯片里的最底层恢复模式。当设备通电时，CPU 首先去 Flash 里找 Loader。如果 Flash 已经被完全擦除（即执行了 ef），CPU 找不到任何可以运行的引导代码，它就会自动降级进入最底层的 MaskROM 模式。
总结： 您执行了 ef 擦除了整片 Flash，导致芯片没有引导程序可以加载，因此无法再进入 Loader 模式，只能自动进入 MaskROM 模式。 一旦您使用 MaskROM 模式成功刷入（uf）新固件，Flash 中就重新写入了引导程序。下次再刷机时，您就可以正常进入 Loader 模式 了。
